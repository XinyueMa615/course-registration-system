# 课程设计改造清单

## 结论

这个旧项目适合作为课程设计的基础，不建议推倒重做。它已经具备学生、教师、管理员三类界面，以及课程、教学班、选课、退课、课表、成绩等基础数据流程。

但它目前只能算“课程注册系统原型”，不能直接作为最终作业提交。题目中特有的注册规则、外部系统接口、安全设计、正式测试和软件工程文档仍需补齐。

## 可以保留的部分

- 三类用户的页面框架
- FastAPI 后端和 MySQL 数据库技术路线
- 学生查看课程、选课、退课、课表和成绩单
- 先修课检查和时间冲突检查
- 教师查看教学任务、名单和录入成绩
- 管理员维护课程、教学班、学生和教师的基础功能

## 必须修改的部分

### P0：先让项目可复现、可协作

- 整理一份可以从空数据库执行的建表与初始化脚本
- 所有本机配置只放在 `.env`，不得写进代码或上传 Git
- 密码改为哈希保存，并增加真正的登录会话和角色权限校验
- 将 1800 多行的单文件后端按学生、教师、管理员、注册流程拆分
- 建立最基本的自动化测试，而不是依赖大量一次性检查脚本

### P1：完成题目核心业务

- 每名学生提交 4 门主选课和 2 门备选课
- 区分“暂存选择”和“正式提交”
- 每个教学班最多 10 人，且并发选课时不能超额
- 教师只能认领自己具备资格教授的课程
- 教务员可以关闭注册
- 关闭注册后取消少于 3 人或没有教师的教学班
- 根据备选顺序自动补位，并重新检查先修课和时间冲突
- 成绩改为 A、B、C、D、F、I 等级制

### P2：补齐接口和质量要求

- 把课程目录封装成“只读遗留系统接口”，业务代码不能直接修改它
- 增加计费系统模拟接口，并实现失败重试和失败记录
- 增加操作日志、异常处理和关键事务
- 完成性能、安全、兼容性和并发测试

## 六人推荐分工

1. 组长兼需求负责人：用例、需求规格、迭代计划、验收清单。
2. 数据库负责人：统一建表脚本、约束、事务、初始化数据。
3. 学生端负责人：4+2 选课、课表、冲突提示和成绩单。
4. 教师端负责人：任课资格、课程认领、名单和等级成绩。
5. 教务端负责人：注册开关、教学班维护、取消与自动补位。
6. 测试与集成人员：登录权限、外部接口模拟、自动化测试、部署说明。

每个人都在自己的 Git 分支开发，通过合并请求进入主分支；不要六个人直接修改同一个主分支。

## 推荐实施顺序

1. 先冻结旧项目，只在当前工作副本修改。
2. 建立统一数据库脚本和演示数据，让六个人都能一键初始化。
3. 拆分后端并完成登录权限。
4. 实现 4+2 注册模型和并发容量控制。
5. 实现教师认领、关闭注册、取消与备选补位。
6. 接入计费模拟和只读目录适配器。
7. 补测试、修界面、整理课程设计文档和演示流程。

## 时间估计

- 能演示的最小版本：6 人集中协作约 5～7 天。
- 符合题目主要要求、测试和文档较完整：约 2～3 周。
- 若只有一两个人实际编码：建议预留 3～5 周。

这个估计以现有数据库能够恢复、组员每天稳定投入为前提。数据库建表脚本缺失或组员分工失衡，会明显延长工期。
